# Daily Review Closeout

Use this skill when a daily reflection is submitted, including a message headed `오늘의 잡상`, `데일리 잡상`, `오늘 회고`, or `데일리 회고`, or dated notes describing that day's experiences. These are triggers on their own; do not wait for an extra request to process them as a review. Do not stop after writing the four-section message.

## Trigger and Slack delivery guard (2026-11-25)

- **Start on the first input.** A message headed `오늘의 잡상`, `데일리 잡상`, or otherwise containing the day's reflections is already the trigger. Begin this workflow in that same turn; do not first send only an acknowledgement, ask whether the skill is running, or wait for the user to request it again.
- **Keep visual QA out of Slack delivery.** In this Slack path, an image block emitted from `functions.exec` with `image(...)` or `generatedImage(...)` becomes its own visible file post. Never use those helpers to inspect the card: that is not an internal preview. First check for a non-posting local visual tool such as `view_image`; a missing paired computer does not mean local image inspection is unavailable. Inspect the final PNG privately and do not forward the viewer result. If no private visual inspection path is available, mark visual QA blocked; do not create a second Slack image as a workaround.
- **Send the card once.** In Slack, send the final review text as a text-only message in the original thread, then use exactly one `message(action="upload-file")` call for the validated PNG in that thread. Do not put the PNG in text-message attachments, emit a screenshot/image block, or retry an upload whose receipt is uncertain; inspect the original thread first. The explicit upload is the only permitted Slack media post for this closeout.
- **Verify one visible image.** Read the original thread after delivery and confirm the review text and exactly one final PNG are present. Count the thread's actual file attachments, not just tool receipts. If a duplicate file-only post appears, delete only the confirmed redundant post by its message timestamp, re-read the thread, and confirm one final PNG remains before reporting completion.

## Required sequence

**One closeout run means prepare → verify → deliver.** The review body being written or sent is not completion. Do not send the four-section review as an early standalone reply and then leave card/calendar work for a later turn. Prepare every deliverable before the final user-facing closeout.

1. Read `/home/ubuntu/workspace/knowledge-lab/source/openclaw-system/docs/reviews/LOCAL_REVIEW_AUTOMATION.md` and the entire `/home/ubuntu/workspace/prompt-archive/DAILY_ARCHIVE_CARD_PROMPT.md`. These own the current review and card rules. For travel days, confirm current place and next movement with `hj`; do not invent places, feelings, or causes. Omit an unconfirmed city from the card.
2. Determine the review's local date and source evidence. Draft exactly `Keep`, `Problem`, `Action Item`, and `Tomorrow Expectation`; separate user facts from SAM's operational work and keep `Action Item` to one experiment.
   - In `Keep`, distinguish `[사실]` from `[Insight]`; in `Problem`, distinguish `[사실]` from `[Why]`. `Tomorrow Expectation` describes the expected scene or signal from that experiment; the sourced quote belongs in the next-day calendar event. Keep internal tools, file paths, and validation details in `운영 처리` after the four-section body.
   - **Reconcile only relevant Slack DMs:** include the requester's same-day DM when it materially relates to the review. Do not inventory every workspace channel, DM, user, or thread-linked row. Resolve the exact DM channel ID with `conversation-open`; never try to read by user ID alone. Read only that DM's relevant same-day messages/replies and record that one result. If Slack returns `read target channel is not allowed`, `not_in_channel`, or an equivalent access denial, log it once and stop—do not fan out, guess another target, or retry through another tool. Use an explicit same-day correction the requester made in the current thread as evidence; otherwise mark the DM source unavailable. Carry any confirmed completion into the review and remove it from tomorrow's pending list.
3. Save the source evidence and full review to `/home/ubuntu/workspace/knowledge-lab/source/openclaw-system/data/daily-reviews/YYYY-MM-DD-review.md`. If that date already exists, read it and update it with the correction while preserving relevant evidence; do not create another review file. Add only genuinely reusable rules to `data/spaced_repetition_items.json`; otherwise record that none was added.
4. Create one private daily archive card using the current book-page editorial layout in `DAILY_ARCHIVE_CARD_PROMPT.md`: warm ivory paper, top/bottom dotted frame, centered medium-weight serif title with generous separation from the body, bold numbered Keep/Problem/Action Item/Tomorrow Expectation headings, same-size indented body text, generous margins, and the date at bottom right instead of a page number. The main title alone is centered; all four section headings and body paragraphs are left-aligned. Do not center a parent wrapper and let that alignment flow into section headings. Do not add illustration or photo by default. Validate PNG and HTML and inspect the actual render against the exact layout rules; visual symmetry is not authority to override them. If anything fails the reference, fix only that mismatch, rerender, revalidate, and re-inspect before upload.
   - Run `python3 /home/ubuntu/workspace/knowledge-lab/source/openclaw-system/scripts/reviews/validate_daily_archive_card.py FINAL_PNG INDEX_HTML`. Check all seven visual conditions in the card contract and record the render file, private viewer, local time with timezone, and `PASS` or `FAIL: item / observed issue / variable to fix` in the card's `validation.txt`. Passing the validator alone does not complete visual QA.
5. Read existing events, then write or update the same-day 5-minute headline and next-day sourced quote in the `회고` calendar only through `gog`. The next-day quote event runs 21:00–23:59 Asia/Seoul, not all day. Select a new quote for each day; check the previous 30 days of quote events in `회고` and do not reuse any quote from that period. Never create or update daily-review entries in the default/general calendar. Verify the quote's author and exact wording against a reliable text, include its source in the event description, avoid duplicates, and re-read `회고` to verify. If quote sourcing or calendar access fails, record the exact failure and leave the closeout incomplete; do not fall back to a guessed quote or a task event.
   - Use a reliable original text; reject uncertain authorship or known misattributions. Preserve the exact original and a direct source link, and label any translation as a translation. Use `<quote> — <author>` as the title without a fixed prefix. If a quote event already exists for that date, update it even when the wording or title changes. Re-query the target calendar to verify dates, timezone, times, wording, and source. Do not query the default/general calendar for this workflow.
6. Prepare one internal Threads demand-validation candidate from an actual same-day user statement. If no such source exists, record the reason for skipping it. Before saving a final candidate, run `python3 /home/ubuntu/workspace/knowledge-lab/source/openclaw-system/scripts/reviews/threads_gate.py CANDIDATE_FILE`; on failure, rewrite once and rerun. If it still fails, skip the candidate and record `게이트 미통과로 생략`. Save only a passing candidate and never publish it without separate approval.
7. Before delivery, re-read the review file and verify the four sections, card render check, the `회고` calendar re-query, Spaced decision, Threads candidate/gate, and delivery asset. Confirm the default/general calendar was not modified. Correct any mismatch now. If an event date is already past, record that it was added retrospectively rather than silently moving it.
8. Only after preparation and checks, send the complete four-section review plus a concise `운영 처리` block in the original Slack thread. Attach the validated final daily archive PNG (1080×1350) in that same thread; if the channel tool requires separate text and media calls, send them consecutively as one closeout and verify both receipts before reporting completion. Never substitute the source illustration, HTML, or a path for the final PNG.
   - After verification and delivery, update the saved review's `운영 처리` with `마감 검증: PASS`, the final PNG and HTML paths, and the `회고` calendar re-query timestamp. Keep incomplete or failed steps explicitly incomplete rather than writing this completion marker early.
9. If a required step fails after reasonable recovery, send one closeout that clearly says `미완료`, identifies the exact failed step and next action, and does not imply success. Do not report `완료` until the user-facing review and final PNG attachment receipts are both confirmed.

## Output boundary

After the four sections, append only a concise `운영 처리` block listing the saved file, Spaced result, card validation, calendar result, and Threads candidate. Never expose credentials, raw logs, or unverified travel details.
