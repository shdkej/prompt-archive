# 데일리 회고 마감

확정 회고로 카드만 만들거나 검수해 달라는 요청에는 [카드 제작 규격](references/card_layout.md)을 적용한다. 이 경우 HTML·최종 PNG·검수 기록을 반환하면 작업이 끝난다. 아래 마감 절차는 회고 전체를 맡긴 경우에 적용한다.

`오늘의 잡상`, `데일리 잡상`, `오늘 회고`, `데일리 회고`로 시작하는 메시지나 날짜가 붙은 하루 경험 기록 등 일일 회고 입력이 들어오면 이 스킬을 사용한다. 입력 자체가 실행 조건이므로 회고로 처리해 달라는 추가 요청을 기다리지 않는다. 4단 회고 본문을 작성하는 데서 멈추지 않는다.

## 실행 범위와 정본

- **사용자 회고 입력:** 아래 전체 마감 절차를 수행한다. [글쓰기 기준](../../../WRITING.md)의 「글과 댓글」·「회고」·「선호 반영」을 먼저 읽는다. 문체 기준의 Headline·Cut·Core·Logic 예시는 판단을 돕는 자료이며, 출력은 이 스킬의 네 섹션을 유지한다.
- **확정 회고의 카드만 요청:** [카드 제작 규격](references/card_layout.md)만 적용한다. 캘린더·Spaced·Threads 후보·Slack 전달까지 요청된 것으로 확대하지 않는다.
- **예약 리마인더:** 21시 크론은 짧은 대화 요약·복습 질문을 전달하는 별도 흐름이다. 크론 호출 자체를 사용자 회고 입력으로 해석해 전체 마감을 실행하지 않는다. 현재 일정·출력·전달 계약은 Knowledge Lab `docs/reviews/LOCAL_REVIEW_AUTOMATION.md`의 「현재 예약 리마인더」를 따른다.
- 공통 부팅·작업 판단은 [LLM.md](../../../LLM.md)와 [DECISIONS.md](../../../DECISIONS.md), 문장은 `WRITING.md`, 카드 조판은 `references/card_layout.md`, OpenClaw 예약·저장·발송은 Knowledge Lab 운영 문서가 소유한다. 공통 기준을 이 스킬에 복제하지 않는다.

## 실행 조건과 Slack 전달 규칙 (2026-11-25)

- **첫 입력에서 시작한다.** `오늘의 잡상`, `데일리 잡상`으로 시작하거나 그날의 회고를 담은 메시지는 이미 실행 조건을 충족한다. 같은 턴에서 이 흐름을 시작한다. 수신 확인만 먼저 보내거나, 스킬 실행 여부를 묻거나, 사용자의 재요청을 기다리지 않는다.
- **육안 검수와 Slack 전달을 분리한다.** 이 Slack 경로에서는 `functions.exec`에서 `image(...)` 또는 `generatedImage(...)`로 내보낸 이미지 블록이 사용자에게 보이는 별도 파일 게시물이 된다. 이는 내부 미리보기가 아니므로 카드 검수에 이 함수를 쓰지 않는다. 먼저 `view_image`처럼 게시하지 않는 로컬 이미지 도구가 있는지 확인한다. 페어링된 컴퓨터가 없다는 이유만으로 로컬 이미지 검수가 불가능하다고 판단하지 않는다. 최종 PNG는 비공개로 확인하고 뷰어 결과를 전달하지 않는다. 비공개 검수 수단이 없으면 육안 검수를 차단 상태로 기록한다. 우회하려고 Slack에 두 번째 이미지를 올리지 않는다.
- **비공개 뷰어는 직접 호출한다.** `view_image` 같은 로컬 뷰어를 `functions.exec` 안에서 실행할 때 `image(result.image_url)`로 결과를 전달하거나, 뷰어 반환 이미지를 `image(...)`/`generatedImage(...)`로 다시 내보내지 않는다. 이 출력은 사용자에게 보이는 Slack 이미지 게시물이 된다. 가능하면 `view_image` 도구를 별도로 직접 호출해 내부에서만 확인하고, 직접 호출 경로가 없으면 다른 비공개 로컬 뷰어를 찾는다. 확인용 이미지는 Slack·현재 대화·첨부 파일 어디에도 보내지 않는다.
- **카드는 한 번만 보낸다.** 원래 Slack 스레드에 최종 회고 본문을 텍스트만으로 보낸 뒤, 같은 스레드에 검증된 PNG를 `message(action="upload-file")` 호출 한 번으로 올린다. 텍스트 메시지에 PNG를 첨부하거나 스크린샷·이미지 블록을 출력하지 않는다. 업로드 영수증이 불확실하면 재시도하기 전에 원래 스레드를 확인한다. 이 명시적 업로드만 해당 회고 마감의 Slack 미디어 게시로 허용한다.
- **실제 이미지가 한 장인지 확인한다.** 전달 후 원래 스레드를 다시 읽어 회고 본문과 최종 PNG 한 장이 있는지 확인한다. 도구 영수증뿐 아니라 스레드의 실제 파일 첨부 수를 센다. 파일만 담긴 중복 게시물이 있으면 중복임이 확인된 게시물만 메시지 타임스탬프로 지정해 삭제한다. 스레드를 다시 읽고 최종 PNG 한 장만 남았는지 확인한 뒤 완료를 보고한다.

## 필수 실행 순서

**한 번의 회고 마감은 준비 → 검증 → 전달까지다.** 회고 본문을 작성하거나 보냈다고 완료된 것이 아니다. 4단 회고를 먼저 단독 답변으로 보내고 카드·캘린더 작업을 다음 턴으로 미루지 않는다. 사용자에게 최종 마감을 전달하기 전에 모든 산출물을 준비한다.

1. `/home/ubuntu/workspace/knowledge-lab/source/openclaw-system/docs/reviews/LOCAL_REVIEW_AUTOMATION.md`를 읽는다. 여행 중에는 `hj`에게 현재 장소와 다음 이동을 확인한다. 장소·감정·원인을 만들지 않고, 확인되지 않은 도시는 카드에서 생략한다.

2. 회고의 현지 날짜와 원문 근거를 확인한다. 본문은 정확히 `Keep`, `Problem`, `Action Item`, `Tomorrow Expectation` 네 섹션으로 작성한다. 사용자의 사실과 SAM의 운영 작업을 구분하고, `Action Item`은 실험 한 가지로 제한한다.
   - `Keep`에서는 `[사실]`과 `[Insight]`를, `Problem`에서는 `[사실]`과 `[Why]`를 구분한다. `Tomorrow Expectation`에는 그 실험에서 기대하는 장면이나 신호를 쓴다. 출처를 확인한 명언은 다음 날 캘린더 이벤트에 둔다. 내부 도구·파일 경로·검증 상세는 4단 본문 뒤의 `운영 처리`에만 적는다.
   - **관련 Slack DM만 대조한다.** 요청자의 당일 DM이 회고와 실질적으로 관련 있을 때만 반영한다. 워크스페이스의 모든 채널·DM·사용자·스레드 연결 항목을 나열하지 않는다. `conversation-open`으로 정확한 DM 채널 ID를 확인하고, 사용자 ID만으로 읽기를 시도하지 않는다. 해당 DM에서 관련된 당일 메시지·답글만 읽고 그 조회 결과만 기록한다. Slack이 `read target channel is not allowed`, `not_in_channel` 등 접근 거부를 반환하면 한 번 기록하고 조회를 멈춘다. 탐색 범위를 넓히거나 다른 대상을 추측하거나 다른 도구로 재시도하지 않는다. 요청자가 현재 스레드에서 당일 사실을 명시적으로 정정했다면 그 내용을 근거로 쓰고, 그렇지 않으면 DM 소스를 이용할 수 없다고 표시한다. 완료가 확인된 일은 회고에 반영하고 내일의 미완료 목록에서 뺀다.

3. 원문 근거와 회고 전문을 `/home/ubuntu/workspace/knowledge-lab/source/openclaw-system/data/daily-reviews/YYYY-MM-DD-review.md`에 저장한다. 같은 날짜 파일이 있으면 먼저 읽고 관련 근거를 보존하면서 정정 내용을 반영한다. 별도 회고 파일을 중복 생성하지 않는다. 실제로 재사용할 수 있는 규칙만 `data/spaced_repetition_items.json`에 추가하고, 없으면 추가하지 않았다고 기록한다.

4. [카드 제작 규격](references/card_layout.md) 전문을 읽고 확정된 회고의 비공개 카드 한 장을 만든다. 최종 PNG·HTML과 검증기 결과를 확인하고, PNG를 직접 열어 확인한 기록을 카드 폴더의 `validation.txt`에 남긴다. 재렌더한 경우 최종본으로 재검증한 뒤 업로드한다.

5. 기존 이벤트를 조회한 뒤 `gog`로 `회고` 캘린더에만 당일 5분 헤드라인과 출처를 확인한 다음 날 명언을 생성하거나 갱신한다. 다음 날 명언은 종일 일정이 아니라 Asia/Seoul 기준 21:00–23:59 시간 이벤트로 기록한다. 매일 새 명언을 고르고, `회고` 캘린더의 최근 30일 명언 이벤트를 확인해 그 기간에 쓴 문구는 재사용하지 않는다. 기본·일반 캘린더에 데일리 회고 항목을 생성하거나 수정하지 않는다. 신뢰할 수 있는 문헌으로 명언의 저자와 정확한 문구를 검증하고 이벤트 설명에 출처를 넣는다. 중복을 막고 `회고` 캘린더를 다시 조회해 확인한다. 명언 출처 확인이나 캘린더 접근에 실패하면 정확한 실패 내용을 기록하고 마감을 미완료로 남긴다. 추측한 명언이나 할 일 이벤트로 대체하지 않는다.
   - 신뢰할 수 있는 원전을 사용한다. 저자가 불확실하거나 오인용으로 알려진 문구는 제외한다. 정확한 원문과 직접 확인할 수 있는 출처 링크를 보존하고, 번역문에는 번역임을 표시한다. 제목은 고정 접두사 없이 `<인용문> — <저자>`로 쓴다. 같은 날짜에 명언 이벤트가 있으면 문구나 제목이 바뀌어도 기존 이벤트를 갱신한다. 해당 캘린더를 재조회해 날짜·시간대·시작과 종료 시각·문구·출처를 확인한다. 이 작업에서는 기본·일반 캘린더를 조회하지 않는다.

6. 사용자의 실제 당일 발화에서 내부 검토용 Threads 수요검증 후보 한 개를 준비한다. 해당 근거가 없으면 생략 사유를 기록한다. 후보를 만들 때는 [WRITING.md](../../../WRITING.md)의 「Threads 글 작성」·「Threads 말투」·「Threads 발행 전 검수」와 [keyword-title](../keyword-title/SKILL.md)의 `threads` 모드를 적용한다. 여러 첫 줄·각도를 비교하되 최종 저장 후보는 한 개다. 최종 후보를 저장하기 전에 `python3 /home/ubuntu/workspace/knowledge-lab/source/openclaw-system/scripts/reviews/threads_gate.py CANDIDATE_FILE`을 실행한다. 실패하면 한 번 다시 작성하고 재실행한다. 다시 실패하면 후보를 생략하고 `게이트 미통과로 생략`을 기록한다. 통과한 후보만 저장하며 별도 승인 없이 공개 발행하지 않는다.

7. 전달 전에 회고 파일을 다시 읽고 네 섹션, 카드 렌더 검수, `회고` 캘린더 재조회, Spaced 반영 판단, Threads 후보·게이트, 전달할 파일을 확인한다. 기본·일반 캘린더를 수정하지 않았는지도 확인한다. 불일치는 이 단계에서 바로잡는다. 이미 지난 날짜의 이벤트라면 날짜를 임의로 옮기지 않고 소급 등록했음을 기록한다.

8. 준비와 검증을 마친 뒤에만 원래 Slack 스레드에 4단 회고 전문과 간결한 `운영 처리` 블록을 보낸다. 같은 스레드에 검증된 최종 데일리 아카이브 PNG(1080×1350)를 첨부한다. 채널 도구가 텍스트·미디어 호출을 분리하도록 요구하면 한 번의 마감 처리로 연속 전송하고, 두 영수증을 모두 확인한 뒤 완료를 보고한다. 최종 PNG를 원본 삽화·HTML·경로 텍스트로 대신하지 않는다.
   - 검증과 전달이 끝나면 저장된 회고의 `운영 처리`에 `마감 검증: PASS`, 최종 PNG·HTML 경로, `회고` 캘린더 재조회 시각을 기록한다. 완료 표기를 미리 쓰지 않는다. 미완료·실패 단계는 명시적으로 미완료로 남긴다.

9. 합리적인 복구를 시도한 뒤에도 필수 단계가 실패하면 `미완료`를 명시한 마감 메시지를 한 번 보낸다. 정확히 실패한 단계와 다음 행동을 밝히고 성공한 것처럼 표현하지 않는다. 사용자에게 보낸 회고 본문과 최종 PNG 첨부의 영수증이 모두 확인되기 전에는 `완료`라고 보고하지 않는다.

## 출력 범위

4단 본문 뒤에는 저장 파일·Spaced 결과·카드 검증·캘린더 결과·Threads 후보를 담은 간결한 `운영 처리` 블록만 덧붙인다. 자격증명·원시 로그·확인되지 않은 여행 정보는 노출하지 않는다.

이 비공개 회고 마감은 Telegram 리마인더, 공개 카드뉴스 배포, Threads 자동 발행을 허용하지 않는다.
