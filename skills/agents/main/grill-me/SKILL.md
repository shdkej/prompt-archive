# Grill Me

계획이나 설계를 바로 실행하지 않고, 먼저 모호함과 빠진 결정을 드러내는 인터뷰 모드입니다.

원본 `grill-me` 스킬은 Matt Pocock의 `mattpocock/skills`에서 가져왔고, 이 워크스페이스에 맞게 한국어 운영 방식과 OpenClaw의 "스스로 확인 가능한 것은 먼저 확인" 원칙을 보강했습니다.

## Usage

```text
/grill-me [계획, 설계, 아이디어, 작업 요청]
```

또는:

```text
grill me 해줘
이 계획 꼬치꼬치 물어봐줘
시작 전에 날카롭게 검증해줘
```

## Core Behaviors

1. **모든 요청을 먼저 판정한다** - 확인 가능한 사실은 직접 확인하고, 결과·범위·성공 기준·비가역 경계가 달라질 불확실성이 있으면 질문합니다. 단순 조회·사실 질문·이미 확정된 저위험 실행은 질문 없이 처리합니다.
2. **한 번에 하나씩 묻는다** - 여러 질문을 한꺼번에 던지지 않고, 답변에 따라 다음 질문을 좁힙니다.
2. **추천 답도 같이 준다** - 질문만 던지지 않고, 현재 정보 기준의 권장 답이나 기본값을 함께 제시합니다.
3. **코드베이스로 답할 수 있으면 직접 확인한다** - 파일, 문서, 대시보드, 웹, 기존 기록으로 확인 가능한 질문은 사용자에게 넘기기 전에 먼저 확인합니다.
4. **선택지는 지원 채널의 inline button으로 보내고 수신까지 검증한다** - Telegram DM과 Slack처럼 `presentation` 버튼을 지원하는 채널에서는 poll/번호 텍스트보다 버튼을 우선합니다. 버튼을 보낸 것만으로 성공 처리하지 않고, 다음 inbound에서 `callback_data: ...` 또는 Slack `block_action`의 동일한 `value`처럼 callback payload가 실제로 들어왔는지 확인합니다.
5. **callback 수신 후 즉시 이어간다** - callback은 단순 알림이 아니라 사용자의 결정 이벤트입니다. 수신을 확인하면 원래 질문의 스레드·메시지·결정 트리를 다시 읽고, 같은 턴에서 다음 질문 또는 승인 범위 내 다음 액션을 실행합니다. callback을 받았는데 `대기`, `활성 작업 없음`, `다음 지시 필요`로 종료하지 않습니다.
6. **Slack 응답을 실제로 발송한다** - Slack에서는 callback 처리 결과를 일반 최종 텍스트로만 반환하지 않고 `message(action="send")`로 원래 스레드에 보냅니다. 그래야 사용자가 선택 확인과 후속 응답을 볼 수 있습니다.
7. **결정 트리를 따라간다** - 사용자, 성공 기준, 범위, 제약, 리스크, 운영, 배포, 비용, 승인 경계를 차례로 닫습니다.
8. **모호함을 숨기지 않는다** - 애매한 표현, 서로 충돌하는 조건, 검증 불가능한 성공 기준은 바로 지적합니다.
9. **실행 전 짧은 스펙으로 잠근다** - 충분히 물은 뒤, 합의된 결정과 아직 열린 질문을 짧게 정리합니다.

## 질문 전 판정

다음 중 하나라도 해당하면 명시적 요청이 없어도 grill-me 질문을 시작합니다.

- 산출물의 형태나 사용처가 둘 이상으로 해석된다.
- 성공 기준, 제외 범위, 우선순위가 빠져 있어 결과가 크게 달라진다.
- 웹·앱·문서·이미지·콘텐츠·자동화처럼 만들 결과물이 생긴다.
- 공개·비용·권한·계정·삭제 등 별도 승인이 필요한 경계가 있다.

아래는 질문을 시작하지 않는 대표 사례입니다.

- 파일 위치, 현재 상태, 단일 사실을 묻는 조회
- 설명이나 조언만 요청한 질문
- 사용처·형식·범위가 이미 분명하고 되돌릴 수 있는 작은 실행

판정이 애매하면, 질문을 생략하는 쪽이 아니라 결과를 가장 크게 바꿀 한 가지를 묻습니다.

### 판정 사례

| 요청 | 기본 처리 |
| --- | --- |
| "Agent Wiki를 Knowledge Lab에 통합해줘" | 통합의 의미, 산출물, 공개·배포 범위를 한 가지 질문으로 먼저 닫습니다. |
| "유튜브용 설명 페이지 샘플 만들어줘" | 정적 목업인지 실제 배포 페이지인지 한 가지 질문으로 먼저 닫습니다. |
| "이집트의 의외의 사실이 있나?" | 사실을 확인해 바로 답합니다. |
| "1인 생산자는 어디에 돈을 써야 하나?" | 판단 기준(예: 현금 런웨이·성장 투자)을 한 가지 질문으로 먼저 닫습니다. |
| "유튜브 120개 제목 목록 파일 경로는?" | 경로를 찾아 바로 답합니다. |

## Workflow

1. 요청을 한 문장으로 재진술합니다.
2. 이미 확인 가능한 맥락을 먼저 봅니다.
   - 관련 파일, 기존 intent, Knowledge Lab, 대시보드, 브라우저, 공개 문서
   - 단, 공개 게시, 결제, 권한 변경, 시크릿 변경, 최종 계정 생성 같은 비가역 행동은 하지 않습니다.
3. 가장 큰 불확실성 하나부터 질문합니다.
4. 사용자의 답을 받은 뒤:
   - 결정된 것
   - 새로 열린 질문
   - 충돌 또는 리스크
   - 다음 질문
   을 내부적으로 갱신합니다.
5. 필요한 만큼 반복하되, 보통 5~12개 질문 안에서 멈춥니다.
6. 마지막에 아래 형식으로 닫습니다.

```text
결정된 것:
- ...

아직 열린 것:
- ...

추천 실행안:
- ...

멈춰야 하는 승인 경계:
- ...
```

## Question Ladder

상황에 맞춰 아래 순서에서 가장 중요한 질문 하나만 고릅니다.

1. 누가 쓰는가?
2. 이 작업이 성공했다는 증거는 무엇인가?
3. 이번 버전에서 반드시 빠져야 하는 것은 무엇인가?
4. 사용자가 처음 5초 안에 알아야 하는 것은 무엇인가?
5. 가장 위험한 가정은 무엇인가?
6. 기존 시스템과 충돌하는 지점은 어디인가?
7. 되돌릴 수 없는 행동은 어디서 시작되는가?
8. 검증은 무엇으로 닫을 수 있는가?
9. 실패하면 어떤 흔적을 남겨야 다음에 덜 헤매는가?
10. 지금 당장 실행할 수 있는 가장 작은 단위는 무엇인가?

## Response Style

- 한국어 존댓말로 짧고 날카롭게 묻습니다.
- 칭찬이나 장황한 배경 설명을 줄입니다.
- 질문은 하나씩 합니다.
- 질문마다 `제 추천 기본값은 ...`을 붙일 수 있습니다.
- 지원 채널에서 선택지가 2~4개로 좁혀진 질문은 텍스트 번호나 poll보다 inline button을 우선합니다.
- 버튼 callback 값은 `gm:archive:wa`처럼 짧은 ASCII로 작성합니다. 긴 값, 한글, 공백, 원문 텍스트를 callback에 넣지 않습니다.
- 버튼 전송이 실패하거나 callback 인식이 불확실하면 선택으로 간주하지 않습니다. 사용자가 "눌렀다", "선택했어"라고만 말했는데 callback payload가 보이지 않으면 기본값으로 추정하지 말고 짧은 번호 선택지로 다시 받습니다.
- 사용자가 "그만 묻고 실행해"라고 하면, 지금까지 결정된 범위로 실행합니다.

## Inline Button Pattern

선택지가 있는 `grill-me` 질문은 OpenClaw `message` 도구의 `presentation`으로 별도 버튼 메시지를 보냅니다. poll은 즉시 인식되지 않을 수 있으므로 쓰지 않습니다.

Slack에서는 OpenClaw 정규화 형식인 `presentation.blocks[].type: "buttons"`를 사용합니다. 각 버튼은 `label`, `action: {"type": "callback", "value": "gm:..."}`, `style`을 갖습니다. Slack Block Kit의 `section`/`accessory` 원문을 직접 넣는 방식은 사용하지 않습니다. callback 값은 짧은 ASCII로 유지합니다.

버튼 검증 규칙:

1. 버튼 전송 결과의 `messageId`를 기억합니다.
2. 다음 사용자 입력을 처리할 때 transcript/session history에서 해당 선택의 `callback_data: gm:...` 또는 동일한 callback payload가 들어왔는지 확인합니다.
3. callback payload가 없으면 버튼 선택을 받은 것으로 보지 않습니다.
4. 이때 기본값으로 조용히 진행하지 말고, `버튼 수신이 안 보입니다. 1/2/3으로 답해주세요.`처럼 짧게 fallback을 요청합니다.
5. callback이 정상 수신된 예시는 Telegram의 `callback_data: button_test:like` 또는 Slack의 `interactionType: block_action`과 `value: gm:test`가 함께 들어오는 형태입니다.

Slack 전송 결과의 `kind: card`나 `deliveryStatus: sent`는 버튼 선택이 아닙니다. `messageId`와 스레드를 기억한 뒤, 같은 스레드의 다음 inbound에서 `interactionType: block_action`, `actionType: button`, 원래 버튼과 동일한 `value`가 확인되어야 선택을 확정합니다.

## Callback continuation contract

callback 수신은 이 스킬의 한 사이클이 끝났다는 뜻이 아니라, 다음 사이클을 시작하라는 뜻입니다.

1. **수신 확인**: `callback_data` 또는 동일한 callback payload를 원래 버튼의 `messageId`·스레드·callback 값과 연결합니다.
2. **상태 복원**: 원래 질문과 직전 선택지를 다시 읽어 `결정된 것`, `남은 질문`, `다음 액션`을 복원합니다. 현재 `Active` intent가 없다는 이유만으로 이벤트를 버리지 않습니다.
3. **즉시 진행**: 다음 질문, 로컬 조사, 가역적 실행 중 하나를 같은 응답 흐름에서 시작합니다. 사용자가 다시 “계속해”라고 말할 때까지 기다리지 않습니다.
4. **승인 경계**: 외부 발송·공개·결제·권한 변경처럼 추가 승인이 필요한 지점이면 그 지점까지 준비한 뒤 `Waiting`으로 전환하고, `blocker`와 `next_action`을 남깁니다.
5. **관측 필드**: 가능하면 `callback_received`, `continuation_started`, `continuation_result`를 실행 기록에 남깁니다. 성공 기준은 `callback 수신 → 다음 액션 시작`이며, 버튼 전송만으로 통과시키지 않습니다.
6. **복구**: callback 값이 수신됐지만 원래 질문과 연결되지 않으면 기본값을 추정하지 말고, 스레드 재조회 후에도 복원할 수 없을 때만 짧은 번호 fallback을 요청합니다.

```json
{
  "action": "send",
  "channel": "telegram",
  "target": "<chat id>",
  "message": "Archive 버튼은 어느 카드에 붙일까요?",
  "presentation": {
    "tone": "info",
    "blocks": [
      {
        "type": "buttons",
        "buttons": [
          {
            "label": "Waiting + Active",
            "action": { "type": "callback", "value": "gm:archive:wa" },
            "style": "primary"
          },
          {
            "label": "All lanes",
            "action": { "type": "callback", "value": "gm:archive:all" },
            "style": "secondary"
          }
        ]
      }
    ]
  }
}
```

## Boundaries

- 이 스킬은 실행을 늦추기 위한 절차가 아닙니다. 불확실성을 줄이면 바로 실행으로 전환합니다.
- 사용자가 이미 명확한 실행을 요청했고 위험이 낮으면, grill-me 관점으로 판정만 하고 질문 없이 실행합니다.
- 비가역 작업 승인 경계는 OpenClaw `AGENTS.md`와 `INFINITY_OPERATING_RULES.md`를 따릅니다.
